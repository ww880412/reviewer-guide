GUIDE / 安装与日常使用

给出材料和目标，
从一条请求开始。

你负责说明这次要作什么决定；Agent 负责组织检查、调用工具和整理证据。常规使用不需要手填 JSON、digest 或任务 ID。

01 / 安装前

先确认你拿到的是哪份代码。

首轮仅适配 Codex。当前 0.7.0 架构重构已完成工程验收；新候选的全新宿主 E2E 与真人体验仍待验证，插件包尚未公开分发；本页没有公开下载包或一键升级按钮。下面是已有本地源码时的安装方法，不会因浏览页面而执行。

  • 具备支持插件、原生异步问题卡与独立子任务的 Codex 宿主。
  • Node 已验证版本为 24.13.0 / 25.4.0，最低兼容版本尚未声明。
  • 插件无 npm 运行依赖，自带固定 Task State SDK 快照。
  • 从提供该候选的独立 checkout 操作，核对 plugins/reviewer 包内容；版本号相同也可能是不同字节。
# 在已核对的 reviewer-plugin 仓库根目录执行
codex plugin marketplace add "$PWD" --json
codex plugin add reviewer@reviewer-local --json

这是 reviewer-local 本地安装源，不是公开市场发布。安装后核对并信任三个实际 hook（SessionStart、UserPromptSubmit、SubagentStop）的 hash，再在新 thread 中开始。

安装后先检查绑定

让 Agent 调用 reviewer_status。若返回 unbound，先处理 hook 绑定；没有可信身份时，插件拒绝写入。不要让 Agent 猜 thread ID 或伪造回执。

02 / 第一次使用

准备材料、依据和这次的目标。

  1. 把文件放进当前项目

    使用明确的项目内相对路径。材料与任务说明、已签核上游依据分别标注；推荐文本或 Markdown，二进制材料先整理为可核对文本。

  2. 选择 Reviewer skill 并描述范围

    在 Codex 选择 Reviewer，或用下方 $reviewer 示例。文件路径是示例，换成你项目内的真实文件。

  3. 确认标准与方案

    新增或冲突项需要你表态；独立审查完成后，再确认检查范围、来源、是否联网与成本上限。

  4. 在最终卡作决定

    检查证据与未解决项，选择接受、附修改建议接受、要求修改、暂缓或拒绝。页面示例不会替你发送决定。

03 / 完整评审

方案准备签核时。

$reviewer
请完整评审 docs/proposal.md。
目标：判断是否满足 docs/task.md 的交付要求。
上游依据：docs/approved-constraints.md（已签核）。
先对齐评审标准和方案，再检查目标覆盖、推理与事实。
先只用项目内来源；是否需要联网、成本上限在方案中确认。

预期路径：对齐 → 独立审查 → 你确认 → 拆单元并检查 → 证据协调 → 最终处置。方案里的新增要求不会因为 Agent 写出来就成为你同意的标准。

04 / 置信把关

不增加项目要求，先查可信度。

$reviewer
请对 docs/research.md 做长材料置信把关。
只使用固定置信规则，检查事实、数字、引用和结论强度。
先确认评审方案与允许来源，不额外增加项目验收标准。

仍会对齐和确认方案；它不是跳过 Loop 1 的快捷开关。来源确实存在但不支持断言，依然不能当作依据。

05 / 仅对齐

正文未完成，也可以先确定验收标准。

$reviewer-align
本次仅对齐评审标准，先不检查材料。
任务说明在 docs/task.md，上游已签核决定在 docs/decisions.md。
请形成标准、范围、排除项、假设和评审方案。

Agent 使用 alignment_only 模式，可尚无正文。完成标准确认与账本记录后交付 final/alignment.md；这不代表材料已经通过。后来要评审材料，须新建评审并重新核对适用性。

06 / 修改后复查

沿原 thread 继续。

$reviewer-recheck
我已修改 docs/proposal.md，请继续当前评审的增量复查。
范围不变。请说明改动影响、重跑的检查、沿用的结果及依据，
最后保留本轮需要我决定的未解决项。

先完成上一轮处置，再进入复查。软件根据材料、标准、来源和依赖计算范围；不是只看你标注改过的段落。范围不变时不重问标准，例外决定仍需真实回复；包括首轮最多三轮。

07 / 人机分工

哪些事需要你回答？

时刻 你需要做什么 Agent 负责什么
标准有新增或冲突 对影响范围、证据或验收的条目表态 给出来源、差异和具体选项；普通实现选择自主处理
开始检查之前 确认整体标准与方案 先完成覆盖和忠实度独立审查
出现业务例外 决定改范围、接受具体检查缺口风险，或超成本放行 说明缺口及后果，保留未解项
最终处置 看结果和证据，接受、修改、暂缓或拒绝 展示本轮有效投影、未覆盖和成本
恢复或结束 在重试耗尽或主动结束时作控制决定 保留失败历史，不把控制决定当成标准确认

在插件生成的原生卡里作答。自由文字可用于讨论，但讨论不等于确认；Skip、空答和沉默也不等于同意。卡片不可用时保留待答状态，不能让 Agent 代答。

08 / 阅读结果

先看影响，再查证据。

1. 看阻断与未覆盖

哪些问题影响结论？哪些规定检查没完成？存在争议，还是确实缺一轮检查？

2. 查标准、原文、来源

问题依据是否属于冻结标准？原文定位准确吗？证据究竟支持、反驳，还是中立？

3. 作本轮决定

当前影子模式不提供自动推荐结论。接受风险也不把“证据不足”变成“通过”。

检查结果 如何理解
pass 该项有核验依据支持通过；仍不是你对整份材料的接受。
needs changes 发现需修改的问题，应能回连标准、原文和证据。
insufficient evidence 证据不足以支持判断；保留不确定性，不强凑通过。
not applicable 有明确范围依据的不适用，不是没有检查。

09 / 投入与数据

预算提前约定，消耗如实记录。

评审方案冻结检查分流、联网范围和正数成本上限。运行中不得为了省钱自行少查、扩源或更换模型；达到上限后先暂停，由成本卡承接你的决定。

standard_credits 是按冻结单价表折算的标准消耗量，不是账单金额、Fast/Ultrafast 实际扣费或订阅使用比例。未知模型使用保守估算并披露，记录不全会标明未完整计量，不能当作零成本。

状态和材料快照保存在本地，但模型调用仍由 Codex 宿主处理；“本地插件”不等于“材料从不离开设备”。是否检索外部来源由已确认方案决定。本地快照、来源和轨迹也应按材料本身的敏感程度保管。

10 / 操作速查

说任务，不必手填工具参数。

你可以这样说 对应行为
“查看 Reviewer 当前状态” 读取 reviewer_status，确认阶段和未答问题。
“继续当前评审” 同 thread 从保存状态恢复；若等待决定，先处理原问题。
“恢复刚才没答的问题” 核对 ticket 后重呈原题；不挪用其他卡的答复。
“这次只对齐标准” 使用 reviewer-align 的仅对齐模式。
“按修改后的文件增量复查” 使用 reviewer-recheck，重新计算影响范围。
“结束这次对齐” 由对应控制卡记录结束，不代表接受材料。
开发者：12 个 MCP 工具分别做什么？

reviewer_start 启动；reviewer_align_submit 提交草案；reviewer_align_build 构建提案；reviewer_assign 派任务；reviewer_collect 从可信宿主收件；reviewer_units_submit 提交单元；reviewer_reconcile 协调；reviewer_finalize 生成最终投影；reviewer_recheck 复查；reviewer_ask 开卡；reviewer_continue 绑定与收集真实回复；reviewer_status 查状态。

阶段由合法动作驱动，没有供模型随意跳步的公开 advance 工具。工具契约以候选源码为准。

11 / 常见问题

遇到中断或不确定状态时。

为什么没有继续检查？

先查 status：可能等待标准确认、未答问题、独立审查、成本放行或故障恢复。pending 是有效状态，不应该靠重建评审绕过。

收件出现 result_binding_mismatch 怎么办？

结果会被拒收。本候选已将对齐阶段同类错误纳入技术失败；第一次可重派一次，耗尽后按相应控制处理。不要接受错误 ID，也不要修改结果冒充通过。

换了对话，还能继承上次的决定吗？

不能。跨 thread 是新评审，不继承旧回执权限；历史标准可作为候选，但仍须核对适用性和必要确认。同 thread 从 status 恢复。

模型判了 pass，为什么还要我决定？

pass 是某项检查的结果；材料是否可用于你的决定，还涉及未解问题、范围和风险。影子模式不替你给出最终建议，更不会代你确认。

Claude 和另外两个判官每次都会参与吗？

不会。日常运行有独立子任务复核；本版验收才使用可配置模型判官和 Claude 独立核验。允许同一 Codex 家族的不同实际模型，不把不同昵称或 effort 当不同模型。

如何升级或回退？

先核对候选 digest 与验收记录，停止旧写入器，再切换包并在新 thread 开始；不要让新旧包同时写同一项目。回退保留新版状态，禁止旧版写入新版状态。当前网站不执行安装更新；本次发布没有切换日常安装。

可以给团队直接使用，或用来做合规认证吗？

当前 V1 按单用户本地流程设计，未承诺多人协作或其他领域的普遍有效性，也不能替代合规认证。先按当前验证范围使用。

Reviewer 先对齐标准，再检查材料，决定留给你。
